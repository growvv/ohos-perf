Why ohos-perf

Closed tools give you answers. This gives you the data.

HapRay and DevEco are excellent at producing a verdict. But their pipelines are opaque, and the emulator cannot produce every signal. ohos-perf exposes each stage as a typed API — and when a signal is unavailable or approximate, it says so instead of inventing a number.

Capability matrix, not guesswork

One probe produces 23 verdicts. Each one records availability, the reason when missing, the evidence command and its output, and the fidelity you should expect.

Deterministic by contract

The same input produces byte-identical JSON across runs. Metrics are sorted by id; evidence is sorted by (kind, window, id). Diffs in CI are meaningful.

Every number is traceable

Metrics carry provenance (collector, table, rows scanned, device) and evidence carries drill-down ids. A claim you cannot trace back to frame_slice is a claim you should not ship.

Honest about the floor

Fidelity is exact, approximate or proxy — never silently upgraded. On an emulator, missing PMU and hiprofiler support is reported with a reason, not a zero.

TypeScript all the way down

Typed queries over 88 tables, an ESM package with a checked public surface, and Node's built-in SQLite. No native build step, no Python, no bundled binary.

Built to be called by agents

The CLI speaks stable JSON, ohos-perf query turns every drillDown handle into the next call, and ohos-perf compare classifies what changed between two captures — including incomparable, which means the direction is unknown rather than nothing changed. skill/ohos-perf/SKILL.md packages that loop, so an agent can go from an evidence item to its frames, callstacks and binder pairs, then check the fix against a baseline, without screen-scraping or parsing prose.

The gesture is inside the window

A scenario step starts the capture, injects its actions while the collectors are running, then awaits the capture — so the tap that caused the work is in the trace, not in a second terminal. setup runs before the window and cleanup after it, so neither pollutes the measurement. A failed action keeps its scene: the trace is still a real measurement of what the device did. Actions record a host-clock atMs, so a gesture is correlatable with the scene's capture.startedAtMs even on devices that refuse /proc/uptime.

Scored against HapRay

Recorded traces pin field-level output for binder, threads and fault tree against HapRay rev 9386e4e. The threads scorer also has a synthetic HapRay golden that exercises the redundancy-scoring path, which the recorded traces cannot: they contain no redundant patterns and no perf samples, so their thread goldens are all-zero. Memory and startup claim no parity.

Analyzers

Nineteen analyzers over one trace. Every finding carries its evidence.

analyze runs all twenty against a scene and merges the result into one report: 80 metrics and 98 evidence items on the recorded emulator trace — memory measure finds no mem.rss rows, the flamegraph and the symbols analyzer no perf_sample rows, frame load no samples at all and native memory no native_hook rows on a plain hitrace capture, so each reports a degraded proxy with the reason — byte-identical across runs. Each analyzer declares the capabilities it needs; when the trace cannot support one, it reports a degraded proxy with the reason instead of a zero.

Architecture

Eight layers. Each one usable on its own.

Start from the transport, or start from a metric. Every layer is a typed seam, so an agent, a CLI command and a library caller walk the same path.

  1. L7

    API / CLI / Skill

    Programmatic API, ohos-perf CLI, named query drill-downs, compare against a baseline, and the shipped ohos-perf agent skill.

  2. L6

    Report

    Metric and Evidence models, provenance, fidelity, stable ordering.

  3. L5

    Analyze

    Nineteen analyzers: frames with stutter levels and 1 s FPS windows, frame load, fault tree, binder, threads, memory, memory measure, native memory, startup, render, GC pressure, VSync, empty frames with load severity, RenderService skips, flamegraph, symbol statistics and component reuse, with a capability matrix that degrades what the trace cannot support.

  4. L4

    Query

    Eleven typed query classes over the 88 tables trace_streamer produces: frames, processes, threads, sched, instant, callstacks, binder, thread state, startup, perf and memory measurements.

  5. L3

    Ingest

    trace_streamer wrapper, scene artifact layout, read-only database handle.

  6. L2

    Collectors

    hitrace, procfs, hiprofiler, hiperf, hidumper, uitest, screenshot and hilog. One collect runs every requested collector concurrently: --procfs memory samples, --hiprofiler --plugins gpu,xpower,nativehook,memory (the memory plugin records per-process process_measure without needing an app), --hiperf perf.data for a debuggable app (converted into a second perf.db), --hidumper render counters, --uitest the UI tree, --screenshot a real screen capture and --hilog the device log for the capture window. --app is required only by the modes that resolve a pid. A failure restores the previous scene's artifacts rather than presenting a partial scene as complete.

  7. L1

    Device

    Device model, one-shot capability probe, cached CapabilityMatrix.

  8. L0

    Transport

    hdc client: shell, port forwarding, file send/recv, target listing, connect.

Use it

Two entry points, same engine.

As a library

import {
  connect, resolveAppIdentity, runAnalyzers, defaultAnalyzers,
  FrameQuery, ProcessQuery, ThreadQuery, CallstackQuery, BinderQuery,
} from '@ohos-perf/core';

// One probe → identity, 20 capability verdicts, evidence.
const device = await connect();
const caps = await device.capabilities();

// Capture, convert with trace_streamer, open trace.db.
const session = await device.collect({
  app: 'com.example.app',
  durationMs: 10_000,
  sceneRoot: 'scenes/demo',
});
const scene = await session.ingest();

// All analyzers, one context. A capability the trace cannot
// support degrades to a named proxy — never a silent zero.
const processes = new ProcessQuery(scene.traceDb);
const result = await runAnalyzers(defaultAnalyzers(), {
  db: scene.traceDb,
  frames: new FrameQuery(scene.traceDb),
  processes,
  threads: new ThreadQuery(scene.traceDb),
  callstacks: new CallstackQuery(scene.traceDb),
  binder: new BinderQuery(scene.traceDb),
  app: resolveAppIdentity(processes, 'com.example.app'),
  window: { startNs: 0, endNs: Number.MAX_SAFE_INTEGER },
  caps,
  deviceId: device.id,
});

console.log(result.metrics, result.evidence);
scene.close();

As a CLI

# Probe the attached device.
ohos-perf doctor

# Machine-readable capability matrix.
ohos-perf caps --json

# Drive the UI first; gestures are their own command.
ohos-perf gesture click 500 800 --json
ohos-perf gesture swipe 500 800 500 200 --velocity 600 --json
ohos-perf gesture key Home --json

# Capture a scene; every collector runs concurrently.
ohos-perf collect --app com.example.app --duration 10 \
  --out ./scene --procfs --hiperf --hidumper --uitest --screenshot --hilog

# Run all analyzers over it.
ohos-perf analyze ./scene --json

# Compare against a baseline capture, by metric and by screen.
ohos-perf compare ./before ./after --json
ohos-perf ui-compare ./before ./after --out ./ui-diff --json

# Inspect a package on disk: no device, nothing extracted.
ohos-perf hap app.hap --out ./hap-report
ohos-perf hap app.hap --json

# Boot an emulator when no device is attached.
ohos-perf emulator list --json
ohos-perf emulator start ProbePhone --timeout 300
ohos-perf emulator stop ProbePhone

# Exit codes are real: a failed analysis is 1.
$ ohos-perf analyze ./missing; echo $?
1

Roadmap

Shipped, next, and deliberately honest.

Every phase below ends the same way: a capability is reported available only when the package can actually drive it, and a missing one carries a reason.

Shipped · v0.2.0

The measurable core

P0–P6: capability probing, six collectors, trace ingest, typed queries, fourteen analyzers with provenance and fidelity, deterministic JSON, baseline comparison and the agent skill. 906 tests at release; the release reported 20 of 21 capabilities available on a Mate 60, and P8 later corrected the coverage row to 19.

Shipped · v0.2.0

The rest of the analysis surface

P6: GC pressure, VSync anomaly periods, empty frames with HapRay's false-positive filters, RenderService skips reverse-traced through NativeWindow, folded flamegraph stacks, and ArkUI component reuse. Every one is pinned against HapRay rev 9386e4e — on the recorded traces where they have data, on synthetic goldens where they do not. HapRay's UI animation diff stays out: it needs per-step pages.json, element trees and screenshots no collector here produces.

Shipped · v0.3.0

Emulator lifecycle

P7: ohos-perf emulator {list,start,stop,create} so CI and an agent can boot their own target instead of relying on an attached device. start waits for bootevent.boot.completed and reports the target collect --target needs; create never downloads an image and prints the exact -install command instead. Verified against a real 6.1.1.200 install: a warm start returns in 4 s, a cold one in 35 s.

Shipped · v0.3.0

Gesture injection, honest coverage

P8: ohos-perf gesture {click,swipe,key,input,text} drives the app through uitest uiInput, reading success from the tool's No Error marker because hdc masks the device exit code. coverage was re-probed against bjc_cov and is now reported unavailable with its measured reason instead of inheriting hiprofiler's presence. The Mate 60 matrix went from 20 to 19 of 21 — the count dropped because a wrong claim was removed.

Measured · not shipped

Deliberately out

`coverage` has no bjc_cov on the Mate 60 and no collector here to consume it; js.heap needs a debug-signed or profilerable app the Mate 60 did not offer, and no analyzer consumes js_heap_*. HapRay's UI animation diff also stays out: it needs per-step pages.json, element trees and screenshots no collector here produces. Each is a measured no with a reason, not a zero.

Shipped · v0.4.0

Report artifacts

P9: ohos-perf report <scene> --out <dir> renders one analysis pass as a typed, versioned model and six artifacts — a self-contained HTML page with no scripts and no network, report.json, summary.json, metrics.csv, evidence.csv and a dependency-free XLSX workbook. Identical inputs and the same package version produce byte-identical files; every metric keeps its provenance and fidelity; a capability-skipped analyzer is a labelled degraded section with the device's own reason, never a hidden zero. --baseline adds the typed comparison to every artifact.

Shipped · v0.5.0

Frame load, stutter, FPS windows

P10: every app frame's sampled-event load from one batched perf_sample read, top-10 loaded frames with thread, symbol and file drill-downs, stutter graded 1–3 against the expected frame and split by ui / render / sceneboard, fixed 1 s FPS windows, and empty-frame load share with a normal / moderate / severe ladder. Four new queries — frames.fpsSeries, frame.load.threads, frame.load.symbols, frame.load.files. Two upstream behaviors are deliberately not ported: the ±1 ms window expansion (which inflates load and is why upstream's empty share can exceed 100%) and high_load_frames (an instruction count compared against a percentage). Without perf samples every load metric is a degraded proxy with a reason, never a zero.

Shipped · v0.6.0

Native memory

P11: hiprofiler's native_hook alloc and free events paired per address — LIFO across reused addresses, partial frees leave a remainder — into a running total with peak (earliest on a tie), trough and end. Live allocations at the peak and at the end are split per callchain, process and thread, resolved through the trace's own frame and data_dict tables, and classified by HapRay's component table (APP, ArkUI, OS_Runtime, RN, Flutter, WEB, KMP, SYS_SDK). A capture with only native_hook_statistic reports end-of-capture bytes as a proxy and never claims a peak or a timeline. Four new queries: mem.native.unreleased, mem.native.callchain, mem.native.timeline, mem.native.categories. "Unreleased" means still allocated when the capture stopped — it is not a leak claim.

Shipped · v0.7.0

Hilog capture and rules

P12: collect --hilog streams the device log for the capture window into hilog.log, parsed at analysis time so a rule change is a re-analysis rather than a re-capture. A typed rule set — { name, regex, groups, conditions } — is evaluated by an AST evaluator with no eval: a malformed regex or expression is a typed error naming the rule, never a silently dropped pattern. HapRay's four CreatePixelMap rules ship as the default. The analyzer reports hilog.lines.count, parsed and unparsed, one count per rule, and one hilog_match evidence item per matching rule with up to five sample messages. Three new queries: hilog.matches, hilog.rules, hilog.around. A scene with no log degrades with a reason; a log with no matches is a real zero.

Shipped · v0.8.0

Declarative scenarios

P13: ohos-perf run scenario.json --out <dir> validates a versioned JSON document whole before the first device call, then runs each step's three phases for real — setup before the capture window, actions inside it concurrently with the collectors, cleanup after it always, including after a failed action. Every (round, step) pair writes a complete scene at <out>/<id>/round-<n>/, so a step is analyzed with the same analyze/report/query as any other capture, plus steps.json, testInfo.json and pids.json. A failed action fails the step and keeps its scene; --keep-going continues and the exit code stays 1. HapRay's Python runner parses setup and cleanup and never executes them, and retries a case until its output is non-empty — neither behavior is ported.

Shipped · v0.9.0

UI capture and diff

P14: collect --screenshot pulls a real screen capture into screenshot.png beside the tree, and ui-compare <a> <b> --out <dir> reports what changed both structurally and by pixel — ui-diff.json, an offline ui-diff.html and two marked PNGs. Trees are matched by node identity (bundleName|type|id|text), so an inserted node is one difference instead of shifting every later comparison as HapRay's index matching does. Pixels are compared by a 64-bit dHash and a bounded diff over a ≤256 px downscale at tolerance 8, both reported with the threshold. The PNG codec is pure TypeScript over Node's zlib: no OpenCV, no Pillow, no native build, and palette/16-bit/interlaced images are refused with a typed error rather than mis-decoded. Different screen sizes are UI_SIZE_MISMATCH, never silently rescaled. HapRay's four broken behaviors — capture filenames its comparator cannot find, a CaptureUI.capture_ui that does not exist, an inverted if not regions that drops animations, and index-based child matching — are not ported.

Shipped · v0.10.0

Offline HAP inspection

P15: ohos-perf hap app.hap reads the package itself — no device, no hdc, nothing extracted to disk. A pure-TypeScript ZIP reader over Node's zlib inflates stored and deflated entries and CRC-checks every read, refusing by name what it cannot read honestly (HAP_ZIP64_UNSUPPORTED, HAP_ENCRYPTED_ENTRY, HAP_UNSAFE_PATH, HAP_CRC_MISMATCH). One pass produces a per-file inventory under HapRay's own category table, a technology stack detected by a typed port of its techstack-config.yaml (Flutter, React Native, Hermes, KMP, Compose Multiplatform, Lynx, Qt, Unity, Taro, Weex, Cangjie and the third-party library rules), and the assets worth a second look: duplicate groups confirmed by SHA-256 after a (size, crc32) grouping, and files above their category's threshold. Every match names the rule that decided it; a rule requiring metadata matches only when the file itself yields it. --out writes hap.json and an offline hap.html through the same report model as a captured scene. HapRay's ROI, UX scores and "estimated savings" are not ported — none of them is a measurement.

Shipped · v0.11.0

Symbols that are real

P16: a real perf.db showed that frame resolution was wrong in a way no fixture revealed. perf_callchain.name is not a symbol but a data_dict id, and the old code fell back to the first perf_files row of a file when the exact pair missed — inventing names for 1,972 leaf frames (7.14% of all samples). Resolution is now exact (file_id, symbol_id) only, then data_dict, never a neighbour. The symbols analyzer reports the weight it could name and the weight it could not (9.43% on the measured capture), collect --hiperf --so-dir symbolizes at capture time through the device's own trace_streamer, and report writes an offline flamegraph.svg + flamegraph.html from the same folded stacks. New query: symbol.stats.

Shipped · v0.12.0

Scenarios that select and assert

P17: a scenario action used to be a raw coordinate — a claim about one resolution. It is now a selector over the captured UI tree: ten kinds (`text`, `id`, `type`, `clickable`, `all`, `any`, `not`, `index`, `bounds`, `relative`), validated as data with the JSON path in every refusal. `tap`/`tapText` resolve the node and click its centre; a node whose bounds did not parse is refused rather than tapped at (0,0). `scrollTo` swipes its container from 70% to 30% of the height, re-dumping after each swipe, up to five times, and stops at the list's edge — the refusal says how many swipes it actually spent. `swipeArea` and `inputInto` cover carousels and text fields. A step's `expect` block — `present` with `min`/`max`, `absent`, `foreground` — runs against a fresh dump after the actions and before cleanup, records every clause in `steps.json`, and marks the step failed while keeping its scene. HapRay's DSL parses `verify` and never runs it; ours runs. `run --cases

` runs a directory of scenarios as one suite with an anchored `--filter` and a `cases.json` index, refusing an empty match instead of reporting a silent zero-case pass.

Shipped · v0.14.0

Both ways to trace a skipped frame

P19: RenderService skip reverse tracing ran only HapRay's NativeWindow path. It now runs both. The system-API path reads an UnMarsh RSTransactionData event on an RS IPC thread — its name carries the submitting pid (recv data from <pid>) — then follows sched_wakeup back, directly or up to five hops, to the app thread whose frame was submitted. That is what makes ArkUI, RN and KMP skips visible at all. The waste is charged twice over: milliseconds from the traced frame's duration, and rs_skip.cpu_waste.instructions from the app process's sampled weight inside it. rs_skip.traced.rs_api.count and rs_skip.traced.nativewindow.count say which method produced each trace, and every evidence sentence names it. Both new metrics are absent — never zero — when there is nothing to measure.

Shipped · v0.15.0

An animation is not just a moving pixel

P20: ui-compare compared a start/end capture pair structurally and by pixel but emitted no animation label. It does now — and requires both halves to agree. A region is an animation only when its pixels moved and the tree reports a change inside it, because HapRay's pixel-only rule also fires on a blinking cursor, a video frame or a system clock, none of which the app re-rendered. ui-diff.json carries three lists: animations with HapRay's severity bands (major under 50% similar, moderate under 70%, minor under 85%), pixelOnly for the screen moving without the tree, and unmeasuredRegions for regions too small for the 9×8 dHash grid to say anything about. A tree change the pixels did not show is a rendering defect, and is left to the tree diff where it belongs.

Shipped · v0.16.0

A trend only where the runs are comparable

P21: `report` wrote one bundle from one scene, and `compare` compared two. HapRay's multi-version page drew a trend across any files it was handed, because its page had no model that could refuse. `trend --out

` refuses what makes a trend false — fewer than two reports, a duplicate label, two different apps — and makes the rest visible: a metric a run did not emit is a gap, never a zero, and so is a degraded stand-in; a delta runs between the first and last run that actually measured it; a verdict appears only where the metric has a known direction; and the ordering is stated, by capture time when every run recorded one and by argument otherwise. `trend.html` carries an inline SVG sparkline per metric with no scripts and no external resources, and `trend.json` is the same model.

Quickstart

Install, capture, analyze.

Published on npm as @ohos-perf/cli and @ohos-perf/core. Node ^22.13.0 || >=23.4.0, and an hdc + trace_streamer from a DevEco Studio installation.

1

Install the CLI

Globally, or run it once with npx. The library is @ohos-perf/core.

2

Check the device

doctor verifies hdc, trace_streamer and the attached target before anything is captured.

3

Capture a scene

Add --procfs for memory sampling, --cold-start for a launch capture, or --hiprofiler --plugins memory for exact per-process RSS without an app.

4

Analyze offline

No device? Point the analyzer at an existing trace.db and get the same metrics.

$ npm install -g @ohos-perf/cli      # 0.16.0 on npmjs

# Probe the attached device (real or emulator).
$ ohos-perf doctor

# Capture 10s of the app, with memory sampling and a cold start.
$ ohos-perf collect --app com.example.app \
    --duration 10 --out ./scene --procfs --cold-start EntryAbility

# Run all analyzers over the scene, offline.
$ ohos-perf analyze ./scene --json

# Or render an offline report bundle (HTML, JSON, CSV, XLSX).
